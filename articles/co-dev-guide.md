总之，让我们先了解一些非常重要的术语。

### 术语

- **仓库（Repository）**：存储代码和文件的地方。
- **分支（Branch）**：仓库中的一个独立工作区域，用于开发新功能或修复错误。
- **合并（Merge）**：将一个分支的更改合并到另一个分支。
- **拉取（Pull）**：从远程仓库下载代码（Fetch），并合并（Merge）到本地。
- **拉取请求（Pull Request，PR）**：用于提交代码更改并让其他成员审查。
- **签出（Checkout）**：用于在 Git 的不同版本之间进行切换。这个“版本”可以是一个分支（Branch），也可以是一个具体的提交（Commit）。
- **变基（Rebase）**：将一个分支上的所有修改，重新应用到另一个分支的最新提交之上。可能不容易看懂，但后文会解释。

> IDEA 的 Git 集成完全够用，日常开发时，你几乎不用使用 GitHub 的网页端。

## 开始

首先，**请确保你的网络环境可以顺畅地连接到 [GitHub](http://github.com)，它是日常开发的基础**。

### 登录账号

你需要创建并登录自己的 GitHub 账户，并加入开发团队。
随后，在 IDE 内登录你的 GitHub 账号。

### 克隆远程仓库

将远程仓库下载到你的电脑上，通过 IDE 打开，或者在新建项目时选择克隆远程仓库。

## 日常开发

你在仓库的分支列表中会看到两个分支：`dev` 和 `main`，这也取决于你的团队是如何配置分支的。

> 由`dev`, `main`**等分支**组成的开发模式叫做 Git Flow。

`main` 分支（发布分支）是仓库最重要的分支。它的代码是应用的**稳定版本**的代码，在开源项目中，任何人拉取它的代码都可以编译运行。

`dev` 分支（开发分支）是日常开发时提交与合并的目标分支。它存储着经过代码评审的最新代码，但仍可能包含一些未知的错误。**在任何时候，你创建 Pull Request 的目标分支都应该是 `dev` 分支。**

> 请勿在 `main` 或 `dev` 分支上进行直接开发或推送！！！！（你也推送不了，因为一般来说项目管理者都会吧这两个分支设为保护分支，推送将被拒绝。😋）

你可以按照以下步骤进行日常开发：

### 同步最新代码

在你开始开发一个功能时，**一定要确保本地代码是最新的**。
你需要拉取公共仓库 **`dev` 分支**的代码，这个操作会更新你本地仓库的 `dev` 分支。

### 创建特性分支（Feature Branch）

**特性分支**是你马上要开发的功能或特性的 Git 分支。

你需要从 **`dev` 分支**上创建一个新的**特性分支**，这个特性分支的名字描述了你当前要进行的工作。

 
请参考以下的命名规范：

- 新特性：`feature/功能名-日期`，比如 `feature/user-login-2026-3-7`
- Bug 修复：`bugfix/简短的问题描述或 issue 编号`，比如 `bugfix/fix-user-cant-login`，`bugfix/issue-114514`

### 阶段性提交

我强烈建议你将一个大功能拆分成一个个小功能。比如你在开发一个点击显示列表的特性，你可以将小功能划分为：编写 Controller、编写 Service、编写 Mapper 等。当你完成一个小功能时，就**可以**将代码提交（Commit）到你的**本地仓库**。

通过这样的**频繁提交**，你可以更好地管理自己正在开发的功能。如果出现了难以解决的错误，你回退版本的代价会小很多。

提交代码时，请写出详细的**提交信息（Commit Message）**。提交信息描述了你这次都干了些什么事。这个信息不光你要看，负责代码评审的同学同样要看。请使用约定式提交的格式：

```
类型(可选的作用域): 描述
[可选的正文]
[可选的脚注]
```

**类型**描述了你提交代码的“目的”，比如：

- `feat`：新功能
- `fix`：修复 Bug
- `docs`：文档编辑

**作用域**描述了你提交代码影响的功能模块/组件，比如：

- `user`：用户功能相关
- `login`：登录相关

**描述**使用简短的语言说明本次提交做了什么，请使用动词开头，尽量简练，结尾不需要任何字符（比如句号）。

- 不推荐的描述
    - `修改了一些代码`
    - `第一次提交`
    - `我今天吃了米饭`
    - `这句话带句号。`
    - `修复了bug`
- 推荐的描述
    - `添加了用户注册表单验证`
    - `删除了废弃的 API`
    - `修改了列表的展示模式`

**正文**详细描述修改或实现的功能。

**脚注**一般不用，在此不做介绍。

以下为提交信息的示例：

```
feat: 添加用户登录功能

· 实现手机号+密码登录
· 实现验证码登录
· 添加登录状态保持
```

```
feat(order): 添加订单取消功能

实现用户取消订单的核心逻辑：

1. 校验订单状态是否可取消
2. 退款处理（调用支付接口）
3. 库存回滚
4. 发送取消通知给用户
```

当你确认功能没有问题、测试通过、写完提交信息后，你就可以将代码提交到你的**本地仓库**。

#### 合并和变基：要用哪个？

它们都用于整合两个分支的修改。

合并：把两个分支的历史和最终代码**合并在一起**。
变基：把一个分支的修改**移植到**另一个分支的最新提交上。

比如你在 `dev` 分支新建了一个特性分支，正在进行开发，并且已经进行了几次阶段性提交。在你开发时，又有别人往主分支上提交了新的代码。
**此时，你的特性分支已经处于落后的状态。**

如果你在此时拉取 `dev` 分支并使用**合并**，两个分支的历史将被连起来。如果很多人都使用合并，提交历史会变得十分不清晰。

如果使用变基，Git 会从你的分叉节点开始，按照时间线逐个应用另一个分支的最新提交，让最后的特性分支看起来就像刚刚从 `dev` 分支分出来的一样。此时，提交历史是一条直线，十分清晰。

> 变基操作的实质是丢弃一些现有的提交，然后相应地新建一些内容一样但实际上不同的提交。

所以，变基其实就是一种特殊的合并方式，它清理你的提交历史，使其变得更好看。

如同上文的引用部分，变基会创建新的提交 ID。当这种事情发生在远程仓库，是**非常危险的！！！！** 因为别人可能基于之前的提交进行开发，当 ID 不一致时，Git 就蒙了，从而产生**十分严重的问题！！！** 所以这里有一个非常重要的原则：

:::warning
不要对已经推送、且可能有其他人基于其进行开发的提交执行变基。变基只应用于清理你本地尚未共享的提交历史。如果确实需要对已推送的个人分支变基，必须使用 --force-with-lease 强制推送，并确保没有他人在该分支上工作。
:::

我承认这些概念确实有点难理解（我看了也很费脑子）。总之，如果你不确定自己在操作两个分支时会不会干翻所有人和代码库，保险起见，**请使用合并，不要用变基**。

### 正式提交 | 推送与 PR

当你完成了一个完整功能模块的开发，就可以进行**推送操作（Push）**。

> 重要：
> 请保证你正处于你正在开发的**特性分支**中，你需要**提交这个分支**。
> `dev` 分支是受到保护的，无法直接提交。

推送操作会将你更新过的代码提交到远程仓库中。

你需要创建 PR 请求，随后负责代码评审的同学会处理你的 PR。之后，你需要对 PR 请求做出响应。

进行推送操作需要遵循以下大致流程：

**1. 拉取最新代码**

- 签出（就是切换的意思）到 `dev` 分支，进行更新操作
- 把 dev 分支合并/变基到你的特性分支

**2. 解决冲突（如果有）**

- 在合并时，IDE可能会提示你代码产生了冲突，你需要选择保留哪边的代码（`>>` 与 `<<`），解决冲突后点击应用。
- 冲突解决后，请进行功能测试。

此时，你的特性分支会和他人的进度同步。

**3. 推送到远程**

你需要将你的特性分支**直接**推送到远程。远程仓库会创建出一个包含你之前所有提交信息的特性分支。**不要推送 `dev` 或 `main` 分支。**

- 这边出错一般是网络问题，需要自行解决。

**4. 提交 PR 请求**

PR（Pull Request，拉取请求）是将代码修改合并到项目中的提议。

你可以在 GitHub 的 Branches 页面中看到你的特性分支表格行。点击右侧的“创建 Pull Request”按钮，按要求填写对应信息后，即可创建 Pull Request。

在创建 Pull Request 时，你需要：

- 确认 PR 是合并到 **`dev`分支**的
- 确认 PR 是来源于你的**特性分支**的
- 填写 PR 标题与 PR 描述（你做了什么、如何进行测试、注意事项等）

**5. 跟进 PR**

- 你的 PR 可能收到“需要修改”的响应。负责评审的同学会告诉你哪里需要修改。修改完成后，请进行测试并保证没有问题。随后，请**提交修改**，并填写提交信息，而不是**创建新的 PR！！**
- 当 PR 通过后，`dev` 分支的代码就含有你写的那部分了。随后，**你需要同步远程的 `dev` 分支。** 在 IDE 内切换到 `dev` 分支，并进行一次拉取操作。此时你的 `dev` 分支就会和远程仓库的 `dev` 分支同步。
- 上述步骤完成后，我强烈建议你删除本地和远程的特性分支，以使本地仓库简洁。

## 其它 | 注意事项

根据以上步骤操作完，你的本地代码库的当前分支应该回到了 `dev` 分支处。这样，你就可以重复以上操作，继续新功能的开发。

这里是一些注意事项：

1. 请一定要遵守所有开发文档的规范，保证代码质量，避免不必要的 Bug 与返工。
2. 和别人交流时，请保持礼貌！！
3. 在开发功能时，**强烈建议**你同时进行自动化测试的编写！！
4. 在开发时，请和其他开发人员保持持续的交流。
5. 如果遇到问题，你可以：
    1. 问别人（如果人家知道的话）
    2. 问 AI（注意甄别准确性）
    3. 上网找解决方案（注意甄别 AI 生成的文章，网上全是这玩意。你可以去 Stack Overflow 找相关问题的帖子，那种不知名的小博客也不错。在外网找的东西基本都比简中互联网的史有用。）
